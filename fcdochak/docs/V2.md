# FC도착 v2 — 설계와 작업 나누기

**v2 의 한 줄:** 비교해 주는 오픈마켓 → **셀러의 쿠팡 FC 도착 원가를 확정하고 책임지는 운영 플랫폼**으로 옮겨 가는 첫 판.
근거는 2026-09-25 사이트 전수 분석(구조적 모순 8 · 방안 A~F · P0/P1/P2). 9구간 표준화는 그대로 쓴다.

## 지키는 선

- 가지: `fcdochak-v2` 가 v2 의 줄기. 작업 가지 `v2/<꾸러미>` → `fcdochak-v2` 로 합친다. **`main`·`fcdochak`(운영)은 건드리지 않는다.**
- 미리보기: https://fcdochak-v2.vercel.app (Vercel 로그인 필요) · **임시 DB(PGlite)** — Supabase 연결값은 운영에만 있다. v2 의 새 표가 운영 DB 에 들어가지 않는다.
- 미리보기 띠: 환경변수 `PREVIEW_BANNER`(v2 가지에만 `v2`)가 있으면 모든 화면 맨 위에 「v2 미리보기 — 운영 아님」.
- **계약을 떠안거나 돈을 받는 것은 자리만 만들고 스위치는 꺼 둔다.** 확정가·회송 보장·후불·공동 혼적은 화면·계산·기록까지만. 켜는 값은 `fcd.settings` 의 `v2.*` 스위치, 기본 꺼짐.
  근거: 확정가는 국제물류주선업 등록(법인 자본금 3억 원 이상·보증보험)이, 보장은 보험사 제휴가, 후불은 금융사·결제대행 제휴가 전제다. 사람이 정할 일이다.
- 돈 계산은 `src/lib/money` 순수 함수 + `tests/` 시험. 거래 기록은 새 판(`supersedes_id`)으로 쌓고 UPDATE 권한을 주지 않는다.
- 밖으로 나가는 것은 `sendOutbound` · `OUTBOUND_ENABLED` 꺼짐 그대로. 초대 링크는 화면에 보여 주고 복사하게 한다.
- 새 표는 RLS + 정책 + 데모면 `DEMO_TABLES`·걷어내기 시험.

## 꾸러미와 손댈 자리

번호는 겹치지 않게 미리 나눈다. 여러 꾸러미가 같이 만지는 자리(`src/lib/terms.ts`, `seed/demo/index.ts`, `src/lib/server/demo-status.ts`, `src/lib/db/migrations.generated.ts`, `src/components/shell/nav.tsx`, `seed/reference`)는 **덧붙이기만** 하고 기존 줄을 고치지 않는다 — 합칠 때 충돌을 줄인다. 시험은 꾸러미마다 새 파일(`tests/v2-<꾸러미>.test.ts`, `e2e/v2-<꾸러미>.spec.ts`).

### 2차에서 나온 사람이 정할 일 (세 기획 문서에서 모음 — 자세한 근거는 각 문서)

**제휴 구조** (`docs/alliance-plan.md` 10절 · 스위치 `v2.alliance_enabled`)
1. 법률 검토 — 갈래 ①의 준비금 분담·가격 제시가 국제물류주선업 무등록 영업에 해당하는지, 계약서 목차 전체.
2. 첫 제휴 주선사 — 누구와(1~2곳), 어느 구간부터.
3. 책임 비율·상한 — 외부 요인 초과비용 플랫폼 50%·건당 확정가 3% 상한이 맞는지.
4. 수수료율·준비금 적립률 — 3%·30% 가 맞는지, 준비금 보관 방식(별도 계좌·신탁·에스크로).
5. 세무 — 준비금 적립·플랫폼 부담분의 세금계산서·부가세, 월합계 발급.
6. ③ 직접 등록 시점 — 자본금 3억 원 이상·보증보험 1억 원 이상 준비 여부와 시기.
7. 셀러 계약서 — 주선사와 셀러 사이의 확정가 약관(화물 조건 오차·재산정).

**쿠팡 WING 연동** (`docs/wing-plan.md` 11절 · 스위치 `WING_ENABLED`)
1. 쿠팡 문서 원문 확인(이 환경에서 못 열었다) — 키 발급 절차·연동 방식·IP 조건·서명 예시·호출 제한·로켓그로스 입고/바코드/반출 API 유무.
2. WING 입고 목록 엑셀 실물 한 장(개인정보 지운 것)으로 머리글 별칭 확정.
3. 쿠팡 연동 업체(솔루션사) 등록 창구 문의 — 절차·준비물·기간·심사 기준.
4. 고정 IP — 자체개발 방식에 IP 가 필수인지, 필수면 나가는 호출을 어디로 모을지(비용).
5. 폐기한 키 암호문을 DB 에서 없앨지(지우는 SQL 이 필요 — 사람이 만든다).
6. 암호화 키(`WING_KEY_ENCRYPTION_KEY`) 관리 — 누가 만들고 어디에 두고, 바꿀 때 옛 암호문을 어떻게 다시 잠글지.
7. 약관 검토 — OPEN API 이용약관의 제3자 보관·재판매 금지·자료 이용 범위, 개인정보 처리방침 개정 문구.
8. `WING_ENABLED` 를 켤 때 — 1~7 이 끝난 뒤, 미리보기에서 셀러 한 곳으로 먼저.

**셀러 인터뷰** (`docs/research-plan.md` 10절 · 발송 없음)
1. 판정선 확정 — 3%·절반 초과·12명·15%·100명·10 CBM/3 CBM/15%. 바꾸면 설정 `research.rules` 새 판.
2. 동의 문구 법률 검토 후 동의 문구 판을 바꾼다. 검토 전에는 실제 셀러에게 링크를 보내지 않는다.
3. 외부 셀러가 링크를 여는 법 — v2 미리보기는 Vercel 로그인이 걸려 있다. ① Vercel 공유 링크 ② 인터뷰 화면만 운영에 먼저 옮기기(0015 가 운영 DB 에 들어가야 함) ③ 통화 + 인터뷰어 모드만. 미리보기는 임시 DB 라 실제 20명 응답은 ② 또는 ③을 권한다.
4. 사례(상품권) 여부 — 주면 연락처 수집 목적·동의가 늘어난다.
5. 보관 기간이 지난 응답 지우기 — 사람이 SQL 파일을 만들어 실행(자동 삭제 없음).
6. 실험 ③ 업체 섭외 — 콘솔사·포워더에 단가를 물을 사람과 말.
7. 결과를 보고 방안 A 로 옮길지 — 옮기면 제휴 구조·확정가 스위치의 사람이 정할 일이 먼저다.

### 3차에서 나온 사람이 정할 일 (기획 문서 둘에서 모음 — 자세한 근거는 각 문서)

3차의 쿠팡 API 제공(단계 안내·동의·연결 시험·만료 알림) 갱신분은 `docs/sales-plan.md` 에 적었다(`docs/wing-plan.md` 11절은 3차에서 바뀌지 않았다 — 위 2차 WING 목록 그대로 유효).

**쿠팡 API 제공 + 판매 분석** (`docs/sales-plan.md` 8절 · 스위치 `WING_ENABLED` · 설정 `sales.rules` · `wing.egress_ips`)
1. 연동 IP — 고정 IP 를 어디서(고정 IP 프록시·작은 서버) 얼마에. 정하면 설정 `wing.egress_ips` 새 판(여러 개 가능). 비면 단계 안내 4는 「준비 중」. (2차 WING 4번과 같은 결정)
2. 쿠팡 원문 확인 — 로켓그로스 주문·반품·상품·정산 응답 칸, 반품 API 유무, 로켓그로스 상품 API 동의가 읽기에도 필요한지. 확인 전에는 실제 파서를 짓지 않는다.
3. 동의 문구(지금 판 `sales-consent-2026-09b`, 법률 검토 전) 법률 검토 → 판을 올리면 관리자가 다시 동의해야 키를 넣고 쿠팡을 부를 수 있다.
4. 연결을 끊은 뒤 가져온 판매 기록을 지울지·언제(지우는 SQL 은 사람이 만든다). (2차 WING 5번의 키 암호문 지우기와 함께 정한다)
5. 판매 속도에서 품절일을 뺄지(지금은 넣는다 — 재고가 남아 있을 때 보수적. 최근 내내 품절이면 「품절 전 속도」).
6. 판매 분석을 무료로 둘지·유료 기능으로 할지.
7. 만료 알림을 화면을 열 때만 판정하는 지금 방식으로 둘지, 예약 작업을 둘지(예약 작업이면 발송 스위치 `OUTBOUND_ENABLED` 결정도 함께).
8. 설정 `sales.rules` 첫 판(속도 28일·준비일 7일·덮을 일수 60일·ABC 80/95%·곧 품절 21일·실제 원가 최근 5건)이 맞는지.
9. `WING_ENABLED` 를 켤 때 — 2차 WING 1~7 과 위 1~3 이 끝난 뒤, 미리보기에서 셀러 한 곳으로 먼저. 실제 가져오기는 신뢰 경로(`asSystem`, 좁게)로 쓴다(0019).

**소싱처 발굴 — 패밀리 확장 모듈** (`docs/sourcing-plan.md` 12절 · 스위치 `sourcing.enabled` · 설정 `sourcing.rules` · `sourcing.fees`)
1. 패밀리 사이트 이름·도메인(지금 가칭), 별도 도메인이면 로그인 나누는 법.
2. 1단계 시범을 할지 — 현지 소싱 담당(누가, 몇 명, 어디), 처리 기한(5일이 맞는지).
3. 수수료 가정치 — 대행 5% · 샘플 30,000원 · 검품 1일 300,000원이 맞는지. 돈을 받는다면 결제·세금계산서.
4. 책임의 선 약관 문구 — 「소개·조사까지, 발주·대금·품질은 셀러와 공급처」.
5. 지식재산 운영 규칙 — 거절 기준, 권리자 신고 시 후보 내리기.
6. KC 인증 — 인증 필요 품목의 안내 문구, 시험비를 시뮬에 넣을지.

9. 운영 전용 칸(후보 메모·유사도 세부·담당)을 화주가 DB 로 읽지 못하게 칸 나누기/보기 뷰로 막을지 — 켜기 전에 한다(3차 검토 고침에서 남은 것).

1. 이 가설을 시험할지 — 비교실·인터뷰로 견준 뒤(기획 9절 판정선) 이기면 켜기 준비, 지면 걷어내기(기획 11절 순서, 표는 사람이 SQL 을 만들어 백업 뒤 지움).
2. 대행 계약 구조 — 누가 셀러와 계약하나(플랫폼 / 제휴 주선사 — 2차 제휴 구조 재사용 / 중국 현지 창고사) · 계약서(대행 범위·책임 한도·환불).
3. 사입 대금 — 받을지·어떻게(PG·에스크로·선불 충전). 전자상거래법(결제대금예치·소비자피해보상보험)이 B2B 대행에 걸리는지, 선불 충전이 전자금융거래법 선불전자지급수단 등록 대상인지 **확인 필요**.
4. 요금표 첫 판 — 가정치(CBM당·개당·최소 요금·마감 요일)를 콘솔사 실제 단가로 바꿈 → `onestop.tariff` 새 판(`example: false`, 확인일). 2차 인터뷰 「실험 ③ 업체 섭외」와 같은 사람이 물으면 된다.
5. 중국 창고·검품 파트너 — 어디(이우·청도), 검품 기준서, 불량 처리.
6. 보험·보상 — 적하보험, 분실·파손 보상 한도(위 v2 첫 목록의 보험사 제휴와 함께).
7. 혼적 회차 모델 — 여러 셀러 주문 ↔ 한 선적(지금은 화주 하나 선적과만 잇는다).
8. 수입자 명의·관세사 — 셀러 명의 신고를 기본으로 할지, 관세사 제휴, 통관 보류 비용 부담(관세법 제241조·제235조 **원문 대조 필요**).
9. 판정선을 무엇으로 셀지 — 인터뷰에 원스톱 전용 문항 둘(「가격 하나로 맡기겠다 / 비교하겠다」 · 「9구간보다 15%까지 비싸도 맡기겠다」)을 더할지, `fcd.events` 에 원스톱 전환(요금표 → 주문서 → 접수)을 더할지. 더하지 않으면 판정선의 두 숫자는 인용을 사람이 센다.
10. 실제 조직을 지울 수 있는가 — 두 표는 조직에 `on delete cascade`(데모 걷어내기용). 켜기 전에 실제 조직 삭제를 막을지(RESTRICT 로 바꾸는 새 마이그레이션) 정한다.
11. 「남길 말」 자유 글의 개인정보 — 보관 기간·가림 판, 처리방침 개정(중국 창고에 보이는 정보).
12. `onestop.enabled` 를 켤 때 — 2~8·10·11 이 끝난 뒤. 켜도 앱은 결제·메일·문자를 보내지 않는다(결제 연동은 따로 만든다).

### 5차에서 나온 사람이 정할 일 (기획 문서에서 모음 — 자세한 근거는 `docs/tracker-plan.md` 3·5·8·9절)

**통관·입고 알리미** (`docs/tracker-plan.md` 9절 · 환경변수 `UNIPASS_ENABLED` · 설정 `tracker.*`)
1. UNI-PASS 오픈API **원문 확인** — 연계가이드의 요청·응답 칸, 처리구분 낱말 전체 목록(→ 단계 규칙 고침), 호출 한도, IP·도메인 조건, 키 발급 절차(즉시/승인). 이 환경에서는 data.go.kr·unipass 에 접속하지 못했다.
2. 이용약관 — 상업 서비스에서 조회 결과를 보여 주고 **통계로 가공·공개**해도 되는지(업체별 실측 소요 공개 포함).
3. `UNIPASS_ENABLED` 를 켤지, 언제 — 1·2 가 끝난 뒤 미리보기에서 셀러 두세 곳의 실제 번호로 먼저. 켜는 순서는 `docs/DEPLOY.md` 「통관 알리미 예약 작업(크론) 켜기」.
4. 예약 작업(크론)을 켤지·주기 — 호출 한도와 Vercel 요금제(크론 최소 간격)에 맞춰. `vercel.json` 은 사람이 넣는다.
5. 표본 기준(`minSamples` 5)·기간(`windowDays` 90)·일일 한도(500, 그중 공개 150)가 맞는지 — `tracker.rules` 새 판.
6. 공휴일 목록 확인 — 2026~2027 첫 판은 「확인 필요」 표시(제헌절 재지정·음력 날짜). 해마다 누가 새 판을 넣을지.
7. 업체 화면에 실측 통관 소요를 **공개**할지(업체 동의·답변권) — 지금은 `tracker.partner_public_enabled` 꺼짐, 예시 판만. 서로 다른 화주 조직 수 기준을 더할지도.
8. 물류사 화면에 관세청 실측 줄을 보여 줄지(번호는 화주 조직 것 — 화주 동의).
9. 도착일 약속(기획 8절 ①, `tracker.arrival_promise_enabled` 꺼짐) — 보상 범위·재원·보험, 확정가·보장(assure)과 함께.
10. 판매자용 유료 모니터링(기획 8절 ②) — 할지, 값, 결제(결제대행 제휴가 전제).
11. 저장한 번호·단계 기록의 보관 기간과 지우기(지우는 SQL 은 사람이 만든다) · 반출입내용(`rlbrCn`)에 상호·이름이 섞이는지 원문 확인 전까지 저장하지 않는 지금 규칙을 유지할지.
12. 하루 상한을 잠금 안에서 셀지 — 지금은 동시 요청 몇 건이 상한을 넘을 수 있다(켜기 전 확인).
