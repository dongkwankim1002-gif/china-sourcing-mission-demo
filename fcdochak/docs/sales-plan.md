# 쿠팡 API 제공 · 판매 분석 — 기획 (v2 3차 · sales)

> 사람이 읽고 결정하기 위한 문서다. 법률·약관 자문이 아니다.
> 쿠팡에 관한 사실은 **V2.md 「3차」 첫머리**와 **`docs/wing-plan.md`(2차)** 를 따르고 새 주장을 만들지 않는다. 이 문서에서 새로 찾은 것은 출처를 달았고,
> 확인하지 못한 것은 **「확인 필요」**로 적었다. 조사일 2026-09-26. 이 환경에서는 쿠팡 개발자 문서 원문을 열지 못했다(2차와 같다) — 검색 결과의 제목·요약만 보았다.
> 이 작업 중 실제 쿠팡 API 를 한 번도 부르지 않았다.

## 0. 한 줄 요약

- **화주가 자기 쿠팡 OPEN API 키를 FC도착에 맡기는 길을 단계 안내로 다듬고(①), 키를 맡긴 화주에게만 「판매 분석」을 연다(②).**
- 판매 분석의 핵심은 셀러가 매일 머릿속으로 하는 계산 셋 — **「언제 다시 들여와야 하나」(재입고 권장일)**, **「이 상품 정말 남나」(도착원가까지 넣은 실제 마진)**,
  **「보낸 물건이 언제 팔 수 있게 되나」(입고 성과)** — 을 FC도착이 이미 가진 물류 기록(선적·청구·구간 시세)과 쿠팡 판매 기록을 이어서 한 화면에 내는 것이다.
- 쿠팡 호출은 2차 스위치 `WING_ENABLED` 뒤, 기본 꺼짐. 꺼져 있으면 「시험 모드」. 데모는 흉내 어댑터가 만든 180일 예시 판매 기록.
- 키 보관·암호화·흉내 어댑터·엑셀 가져오기는 **2차 wing 을 그대로 쓴다**(새로 만들지 않았다).

## 1. 목적 — 왜

| 셀러가 지금 하는 일 | 판매 분석이 주는 것 | FC도착에 주는 것 |
|---|---|---|
| WING 매출 화면·엑셀을 내려받아 스프레드시트로 판매 속도·재고를 본다 | 상품별 판매 속도(최근 N일 이동평균)·재고 일수·**품절 예상일** | — |
| 품절 날짜를 보고 「중국에서 몇 주 걸리더라」 감으로 발주한다 | **재입고 권장일 = 품절 예상일 − (구간 시세의 운송일 + 준비일)** → 「지금 견적 요청」 한 번에 | **견적 요청이 판매에서 저절로 생긴다** — 물류 수요가 생기는 순간을 잡는다 |
| 개당 마진을 「물품가 + 대충 물류비」로 잡는다 | **SKU 개당 도착원가**(실제 선적·청구 → 없으면 구간 시세) → 쿠팡 수수료 → 실제 마진 · 적자 SKU | 「FC 도착 원가」(V2 한 줄)가 셀러의 손익 한가운데에 놓인다 |
| 반품이 많은 상품을 늦게 안다 | 상품별 반품률·사유 | 회송·불량의 근거 자료(다음 단계에 회송 보장·점수와 잇기) |
| 물류사가 「입고됐다」고 한 뒤 언제 팔 수 있는지 모른다 | **입고 성과**: 선적 FC 입고 → 쿠팡 재고 반영까지 일수 | 업체별 실제 「팔 수 있게 되기까지」 시간(다음 단계에 추천 점수와 잇기) |

## 2. 쿠팡 API — 따르는 사실(V2.md 3차 첫머리)

1. 키는 판매자가 **WING → (판매자정보 →) 추가판매정보 → OPEN API 키 발급**에서 받는다(2차 `wing-plan.md` 2.2 는 「[판매자정보] → [추가판매정보] → [API Key 발급 받기]」, 계정마다 다를 수 있음 — 쿠팡 원문 확인 필요)(업체코드·Access Key·Secret Key). 사업자 인증 판매자만 받고, 권한이 열리기까지 **24시간 이상** 걸릴 수 있다.
2. **로켓그로스 상품 API 는 별도 동의**가 필요하다.
3. 유효기간 **180일** 안내가 있다.
4. 다른 회사 프로그램에 키를 맡길 때는 **그 회사 서버 IP 를 키 설정에 넣는 방식**으로 안내된다.
5. 호출 한도: 판매자당 **초당 5회**, 로켓그로스 주문 조회 **분당 50회**.
6. **로켓창고 재고·로켓그로스 주문·상품 조회 API 는 있다. 입고 생성·바코드 라벨 API 는 찾지 못했다**(WING 화면에서 한다).

이번에 더 찾아본 것(검색 요약, 원문 확인 필요):
- 마켓플레이스 **매출내역 조회 API** 가 있다 — 매출인식일(구매확정 또는 배송완료 뒤 며칠) 기준. 쿠팡 Open API 「매출내역 조회 / Sales Detail Query」
  (https://developers.coupangcorp.com/hc/en-us/articles/360033922413-Sales-Detail-Query). **로켓그로스 상품의 정산이 여기 잡히는지는 확인 필요.**
- 쿠팡 개발자 센터에 「정산 API」 묶음이 있다(https://developers.coupang.com/ko/api — 제목만). 지급내역 조회 기간 제한이 있다는 제3자 안내가 있다 — **확인 필요**.
- 로켓그로스 이용 안내(https://developers.coupangcorp.com/hc/ko/articles/35157075045017) · 로켓그로스 상품 조회
  (https://developers.coupangcorp.com/hc/en-us/articles/37338749441689) — 제목·요약만.
- **로켓그로스 반품 조회 API 는 찾지 못했다 — 확인 필요.** 마켓플레이스 반품·취소 요청 목록 API 가 로켓그로스 주문에도 쓰이는지 모른다.
- 로켓그로스 주문 API 의 **응답 칸 이름(주문 번호·옵션 id·수량·금액·주문 시각)은 원문을 보지 못해 확인 필요.** 그래서 실제 호출기(HTTP)의 주문·반품·상품 파서는 만들지 않았다(지어내지 않으려고).
  재고 요약 경로(2차 어댑터에 있음)는 **「연결 시험」**에만 쓴다 — 응답이 200 이면 연결 확인, 칸은 읽지 않는다.

## 3. 갈래와 고른 것

### ① 제공하는 법
| 갈래 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **가. 판매자 본인 키 + FC도착 IP(자체개발)** ← 고름 | 셀러가 WING 에서 키를 받을 때 연동 IP 칸에 FC도착 IP 를 적고, 세 값을 FC도착에 넣는다 | 쿠팡 심사 없이 시작(2차 wing-plan ①과 같다) | FC도착이 **고정 IP** 를 가져야 한다(Vercel 은 나가는 IP 가 고정되지 않는다 — 사람이 정할 일 1) |
| 나. 연동 업체 목록에 FC도착이 오름 | 셀러는 목록에서 고르기만 | 쉽다 | 신청 창구·심사 확인 필요(2차 사람이 정할 일 3) |
| 다. 셀러가 엑셀만 올림 | 키를 안 맡김 | 약관 걱정이 적다 | 매일 손이 간다 — 판매 분석이 금세 낡는다 |

**가로 시작, 나를 병행, 다는 늘 열어 둔다**(입고 목록·바코드는 어차피 파일 — 2차와 같다). 연동 IP 는 설정 `wing.egress_ips` 에 운영이 넣고, 비어 있으면 화면에 「준비 중 — 운영이 정하면 표시」.

### ② 판매 분석을 누구에게 여나
| 갈래 | 판단 |
|---|---|
| 모두에게(파일 올리기만으로도) | 쉬우나, 「쿠팡 키를 맡기면 얻는 것」이 흐려진다 |
| **키를 맡긴 화주만** ← 고름(지시) | 키가 있는(폐기 안 한) 현재 연결이 있으면 연다. 없으면 **연결 권유 + 예시 미리보기(「예시」 표시)** |
| 유료 | 이번 범위 밖(사람이 정할 일 6) |

- 데모 화주는 키가 없다(2차 원칙: 데모에도 가짜 키 암호문을 두지 않는다). 대신 **데모 조직 + 흉내 동기화 기록이 있으면 「예시 연결」**로 열고 모든 화면에 「예시」를 붙인다.
- 키를 맡겼지만 스위치가 꺼져 있으면(지금 운영 전 모든 실제 셀러) 판매 기록이 비어 있다 → 「시험 모드 — 쿠팡 호출이 꺼져 있습니다」 + 예시 미리보기.
- 실제 셀러의 표에 예시 자료를 넣지 않는다(2차 「예시 가져오기는 데모만」과 같은 규칙). 미리보기는 **저장하지 않고 화면에서만** 만든다.

### ③ 도착원가의 근거
실제 선적·청구 → 없으면 구간 시세(지시). 실제 = 그 SKU 로 올린 견적 요청이 예약·선적된 것 중 **최근 N건(설정)** 의 (현재 판 청구 합계, 청구가 없으면 응찰 합계) + 물품가(환율) + 관세 추정(관세율표) ÷ 수량, 수량 가중.
구간 시세 = 비교 엔진의 추천 순 업체들의 9구간 합계 **중간값**(공개 도구와 같은 `summarizeArrival`). 어느 쪽인지 칸마다 칩으로 보인다(「실제 3건」·「구간 시세」·「원가 없음」).

## 4. 절차 — 셀러 쪽 단계 안내(`/app/integrations/wing`)

```
① WING 로그인 ─ ② 추가판매정보 → OPEN API 키 발급 ─ ③ (선택) 로켓그로스 상품 API 동의
      ─ ④ 연동 IP 칸에 FC도착 IP ─ ⑤ 읽는 것·하지 않는 것 동의 ─ ⑥ 세 값 넣기
      ─ ⑦ 연결 시험 ─ ⑧ 180일 만료 · D-14 알림 · 연결 끊기
```
- 단계마다 「누를 것」을 문장으로, 화면 대신 **메뉴 길 그림**(`WING ▸ 추가판매정보 ▸ OPEN API 키 발급`)과 목록으로 보인다(스크린샷을 싣지 않는다 — 쿠팡 화면이 바뀌면 거짓이 되므로).
- ⑤ 동의 문구(판 `sales-consent-2026-09b` — 9월 첫 판 `sales-consent-2026-09` 에서 「운영자도 키를 볼 수 없습니다」를 사실대로 고쳐 올림, 코드 `src/lib/sales/consent.ts`):
  - **읽는 것:** 상품(옵션) · 주문 · 재고 · 반품 · 정산(API 확인 필요).
  - **하지 않는 것:** 상품 등록·수정 · 가격 변경 · 주문 처리(발주 확인·송장·취소) · 입고 요청 만들기 · 반품 승인 · 문의 답변 — **쓰기 호출은 코드에 없다**(어댑터는 GET 만).
  - 보관: 키는 암호화(2차), 가져온 판매 기록은 그 조직 사람만 본다. 다른 셀러·물류사에게 넘기지 않는다. 연결을 끊어도 이미 가져온 기록은 남는다(지우는 것은 사람이 SQL 로 — 사람이 정할 일 4).
  - 동의는 `fcd.wing_consents` 에 쌓기만(판·범위·누가·언제). 키 저장 서버 행동이 **현재 판 동의가 없으면 받지 않는다.**
- ⑦ 연결 시험: 스위치 꺼짐(또는 흉내)이면 **「시험 모드」** — 쿠팡을 부르지 않고 「키 저장됨 · 지금 암호화 키로 잠김 · 만료일 · 연동 IP 준비 여부」만 본다.
  켜짐이면 관리자만, 로켓창고 재고 요약 GET 한 번 → 200 이면 「확인됨」 새 판, 401/403 이면 「확인 실패」 새 판(2차 규칙 그대로).
- ⑧ 만료: 발급일 + `wing.key_valid_days`(180). 남은 날이 `wing.key_warn_days`(14) 이하가 되면 **알림 표(`fcd.notifications`)에 한 줄**(그 조직 사람 모두, 화면 안 알림만 — `sendOutbound` 를 부르지 않는다 = 발송 없음). 같은 키(발급일)마다 「곧 만료」「만료」 한 번씩(`fcd.wing_key_alerts` 가 중복을 막는다).
  연결 끊기 = 2차 「키 폐기」(폐기 새 판) — 판매 분석은 다음 화면부터 닫힌다.
- 쿠팡 API 로 안 되는 것: **입고 목록·바코드 라벨** → 「WING 파일 올리기」(엑셀·CSV)와 짝 맞은 줄의 「바코드 PDF 올리기」로 안내(2차 기능).

## 5. 판매 분석 화면(`/app/sales/*`)

| 화면 | 보이는 것 |
|---|---|
| 개요 `/app/sales` | 기간(7·30·90일) 매출 · 판매량 · **추정 순이익** · 반품률 — 지난 같은 기간 대비 · 일별 매출 막대 · 주/월 추이 · 매출 상위 · 곧 품절 · 재입고 늦음 |
| 상품별 `/app/sales/products` | 매출 순위 · **ABC**(누적 매출 80%/95% — 설정) · 판매 속도(최근 N일 이동평균) · 재고 · 재고 일수 · 품절 예상일 · **재입고 권장일** · 「지금 견적 요청」 |
| 손익 `/app/sales/pnl` | SKU 평균 실판매가 · **개당 도착원가(근거 칩)** · 쿠팡 수수료·광고·로켓그로스 비용(`tools.coupang_fee_basis`, 예시 기준값 표시) · 개당 이익·마진 · 기간 이익 · **적자 SKU** · 정산 칸은 「확인 필요」 |
| 반품 `/app/sales/returns` | 상품별 반품률 · 사유 순위 · 주별 반품 |
| 입고 성과 `/app/sales/inbound` | 선적 FC 입고(9단계) → 쿠팡 재고에 그 수량의 절반 이상이 반영된 첫날까지 일수(한 상품에 입고가 몰리면 선입선출로 나눠 셈) · 중간값 · 평균 · 업체별 |

「지금 견적 요청」: 권장 수량 = 하루 판매 × (운송일 + 준비일 `prepDays` + 덮을 일수 `coverDays`) − 지금 재고, `roundUnits` 단위로 올림(0 이하면 0 — 코드 `suggestUnits`). 최근 `velocityDays` 내내 품절이라 판매가 0 이면 그 앞 기간 속도(「품절 전 속도」)를 쓴다. SKU 의 박스·무게·부피 비율로 늘려 **기존 견적 요청 화면(`/app/requests/new?sku=…&units=…`)에 채워 넘긴다.** 요청을 대신 올리지 않는다.

### 계산(순수 함수 `src/lib/money/sales.ts` · 시험 `tests/v2-sales.test.ts`)
- 매출·판매량 합계(기간) · 지난 기간 대비(bp) · 주/월 묶음.
- ABC: 매출 큰 순으로 누적 비율이 `abcABp` 이하면 A, `abcBBp` 이하면 B, 나머지 C(경계를 넘기는 상품은 그 등급에 넣는다 — 첫 상품은 늘 A).
- 판매 속도 = 최근 `velocityDays` 일 판매량 ÷ 그 일수(품절이던 날도 넣는다 — 보수적. 사람이 정할 일 5).
- 재고 일수 = 재고 ÷ 속도(내림) · 품절 예상일 = 마지막 재고일 + 재고 일수 · 속도 0 이면 「팔리지 않음」.
- 재입고 권장일 = 품절 예상일 − (운송일 + `prepDays`). 운송일 = 그 SKU 의 최근 선적 구간(없으면 기준 구간)의 유효 요금표 운송일(최대) 중간값, 없으면 방식표 `modes.days_max`. 오늘보다 앞이면 「늦음」.
- 개당 도착원가 = 3절 ③. 개당 이익은 기존 `unitPnl`(판매손익 계산기와 같은 식: 부가세 뺀 매출 − 수수료(판매+광고) − 원가 − 로켓그로스 비용).
- 반품률 = 반품 수량 ÷ 판매 수량(bp).
- 입고 반영 일수 = 재고가 늘기 시작한 날 − FC 입고일(선적 수량의 절반 이상 늘어난 첫 스냅숏).

| 고정 IP 비용 | 사람이 정할 일 1 |

## 8. 사람이 정할 일

1. **연동 IP** — 고정 IP 를 어디서(고정 IP 프록시·작은 서버) 얼마에. 정하면 설정 `wing.egress_ips` 새 판(여러 개 가능). 비면 화면은 「준비 중」.
2. 쿠팡 원문 확인 — 로켓그로스 주문·반품·상품·정산 응답 칸, 반품 API 유무, 로켓그로스 상품 API 동의가 읽기에도 필요한지.
3. 동의 문구 법률 검토 → 판을 바꾸면 `SALES_CONSENT.version` 을 올리고(새 동의 필요) 문구 교체.
4. 연결을 끊은 뒤 가져온 판매 기록을 지울지·언제(지우는 SQL 은 사람이 만든다).
5. 판매 속도에서 품절일을 뺄지(지금은 넣는다 — 품절이 길면 속도가 낮게 나와 재입고가 늦게 권해진다).
6. 판매 분석을 무료로 둘지·유료 기능으로 할지.
7. `WING_ENABLED` 를 켤 때 — 2차 사람이 정할 일 1~7 이 끝난 뒤, 미리보기에서 셀러 한 곳으로 먼저.
8. 설정 `sales.rules` 첫 판(속도 28일·준비일 7일·덮을 일수 60일·ABC 80/95%·곧 품절 21일·실제 원가 최근 5건)이 맞는지.
